Topic
A stream of messages (like a category).
➡ Producers write to topics; consumers read from them.

Partition
Sub-division of a topic for scalability and parallelism.
➡ Each partition is ordered and stores messages sequentially.

Broker
A Kafka server that stores and serves topic data.
➡ Kafka cluster = multiple brokers.

Producer
Sends (publishes) messages to a Kafka topic.

Consumer Group
A group of consumers sharing the workload.
➡ Each partition is consumed by one consumer in the group.

Offset
A unique ID for each message in a partition.
➡ Tracks how far a consumer has read.

Zookeeper
Manages Kafka cluster metadata and broker coordination.
➡ Handles leader election and configuration (used in Kafka pre-2.8).

Coordination Summary:
Producers send messages to topics (divided into partitions) on brokers.
Consumers (in groups) read from partitions using offsets.
Zookeeper coordinates brokers and cluster metadata.

2. Explain how brokers work with topics?
   A Kafka broker is a Kafka server that:
Stores data (topic partitions), Receives data from producers, Serves data to consumers
How Brokers Work with Topics:
Topic Partitioning
A topic is divided into partitions.
Each partition is stored on one or more brokers.
Kafka assigns partitions to brokers for load balancing.

Leader and Replicas
For each partition, one broker is the leader.
Other brokers may hold replicas for fault tolerance.
Producers and consumers interact only with the leader of a partition.

Producer Interaction
A producer sends data to a topic.
Kafka routes the data to a partition (based on key/hash or round-robin).
The broker that leads that partition stores the message.

Consumer Interaction
Consumers pull messages from the broker that holds the leader partition.
The broker reads data from disk and returns it to the consumer.
3. Are messages pushed to consumers or consumers pull messages from topics?
   In Apache Kafka, consumers pull messages from topics — messages are not pushed.
4. How to avoid duplicate consumption of messages?
   Avoiding duplicate consumption of messages in Kafka involves designing for idempotency and using offset management correctly. Here are key strategies:
   1. Idempotent Consumers
Ensure your consumer logic can safely process the same message multiple times without side effects.

   2. Manual Offset Commit (after processing)
Use manual (not automatic) offset commits.
Only commit the offset after the message is successfully processed.

   3. Exactly-Once Semantics (EOS) (Advanced)
Kafka supports exactly-once semantics with:
Set:
properties
enable.idempotence=true
acks=all
transactional.id=your-id
And use Kafka transactions to consume and produce in a single atomic unit.

✅ 4. Store Processed Message IDs (Deduplication)
Maintain a deduplication store (e.g., Redis, DB) of processed message IDs.

5. What will happen if some consumers are down in a consumer group? Will data loss occur? Why?
Consumers down → Partitions reassigned, no data loss by default.
Correct offset and retention config ensures reliability.
6. What will happen if an entire consumer group is down? Will data loss occur? Why?
   If an entire consumer group is down, data loss will not occur as long as Kafka's retention policies and replication settings are configured properly.
   If an entire consumer group is down, Kafka retains messages until consumers are back online (within retention limits).
No data loss unless messages expire or there’s no replication.
7. Explain consumer lag and how to resolve it?
Consumer lag refers to the delay or backlog of messages that a consumer in a Kafka consumer group has yet to process.
   1.Consumer is slow: The consumer may not be processing messages fast enough (e.g., due to resource bottlenecks or inefficient code).
   2.High message throughput: A large volume of messages might be produced faster than the consumer can process.
   3.Consumer group imbalances: If some consumers are idle or underutilized, one or a few consumers may be handling a disproportionate number of partitions.
   4.Network issues: If consumers are experiencing network congestion or timeouts, it can delay message consumption.
   5.Consumer downtime: If a consumer goes down temporarily, it can accumulate lag while it’s not processing.
   | Solution                        | Description                                    |
   | ------------------------------- | ---------------------------------------------- |
   | **Scale Consumers**             | Add more consumers to balance the load         |
   | **Optimize Consumer Logic**     | Speed up message processing by improving logic |
   | **Increase Consumer Resources** | Provide more CPU/Memory for consumers          |
   | **Tune Kafka Configurations**   | Adjust fetch settings for better throughput    |
   | **Monitor Consumer Health**     | Use monitoring tools for early detection       |
   | **Increase Broker Resources**   | Ensure Kafka brokers can handle the load       |

8. Explain how Kafka tracks message delivery?
Kafka tracks message delivery using a combination of offsets, acknowledgments, and replication to ensure that messages are delivered reliably and in order.
   | Concept                    | Description                                                                                           |
   | -------------------------- | ----------------------------------------------------------------------------------------------------- |
   | **Offsets**                | Unique position markers for each message within a partition.                                          |
   | **Acknowledgments**        | `acks` setting to control message durability and guarantees (0, 1, all).                              |
   | **Replication**            | Ensures message availability through replica copies in multiple brokers (Leader & Followers).         |
   | **Consumer Offset Commit** | Consumers track the last successfully processed offset, ensuring no message is missed.                |
   | **Consumer Groups**        | Multiple consumers share the load, and Kafka ensures each partition is consumed by only one.          |
   | **Delivery Guarantees**    | At-most-once, at-least-once, and exactly-once delivery, configurable through `acks` and transactions. |

   | --------------------- | ------------------------------------------ | ----------------------------------------- |
   | **Architecture**      | Distributed log, event streaming           | Centralized broker, message queues        |
   | **Use Case**          | Event-driven, stream processing            | Task queues, messaging between services   |

   | **Consumer Handling** | Consumer groups, replayability             | Round-robin or individual consumers       |
