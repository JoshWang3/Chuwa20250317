Explain following concepts, and how they coordinate with each other: 
Topic
Partition
Broker
Consumer group
Producer
Offset
Zookeeper
---

A **topic** is a named stream of records (like a table in a DB). Producers write to topics, and consumers read from them.

Each topic is split into one or more **partitions**. A partition is an **ordered, immutable sequence** of records. Each record in a partition has an **offset**.

A **broker** is a Kafka server that stores data and serves clients. A Kafka cluster is made up of multiple brokers.

A **consumer group** consists of one or more consumers that work together to consume records from a topic. Each partition is consumed by **only one consumer** in the group.

A **producer** sends records to Kafka topics. It can choose the partition explicitly or use a partitioner (e.g., round-robin or key-based).

An **offset** is the unique ID of a record within a partition. Consumers use offsets to track progress.

Kafka uses **Zookeeper** (until KRaft is fully adopted) to manage cluster metadata, broker health, leader election, and topic configs.

Answer following questions:
1. Given N (number of partitions) and M (number of consumers,) what will happen when N>=M and N<M
respectively?
* If **N ≥ M**: Some consumers handle multiple partitions.
* If **N < M**: Some consumers are **idle**. Kafka assigns only one consumer per partition in a group.


2. Explain how brokers work with topics?
* A topic’s partitions are distributed across **multiple brokers**.
* Each broker stores one or more partitions and serves read/write requests.


3. Are messages pushed to consumers or consumers pull messages from topics?
* **Consumers pull** messages from brokers (pull-based model).


4. How to avoid duplicate consumption of messages?
* Use **idempotent processing** in consumers.
* Enable **exactly-once semantics** (EOS) using Kafka configuration:
```yaml
  enable.idempotence=true
  acks=all
  ```
Consumer can commit offsets **after** successful processing.

5. What will happen if some consumers are down in a consumer group? Will data loss occur? Why?
* Kafka **rebalances** remaining consumers to take over.
* **No data loss** if `auto.offset.reset` is properly set and data is retained.


6. What will happen if an entire consumer group is down? Will data loss occur? Why?
* No data loss **as long as offsets are not committed** and **retention** is configured.
* When restarted, consumers resume from last committed offset.


7. Explain consumer lag and how to resolve it?
* **Lag = latest offset - committed offset**
* High lag means slow consumption.
* Resolve by:

    * Adding consumers
    * Optimizing processing
    * Increasing partition count


8. Explain how Kafka tracks message delivery?
* Kafka tracks offsets per consumer group.
* Consumers commit offsets manually or automatically.
* Delivery guarantees:

    * **At most once**: commit before processing.
    * **At least once**: commit after processing.
    * **Exactly once**: requires idempotent producer + transactional consumer.


9. Compare Kafka vs RabbitMQ, compare messageing frameworks vs MySql (Why Kafka)?

| Feature     | Kafka                   | RabbitMQ              | MySQL                |
| ----------- | ----------------------- | --------------------- | -------------------- |
| Type        | Log-based, distributed  | Queue-based           | Relational DB        |
| Use Case    | Event streaming, logs   | Messaging, workflows  | Structured queries   |
| Throughput  | Very high               | Medium                | Low                  |
| Retention   | Configurable            | Deletes after consume | Persistent (DB rows) |
| Ordering    | Per-partition           | Global per queue      | N/A                  |
| Scalability | Horizontal, partitioned | Horizontal, clustered | Vertical or sharded  |
