2. Explain TLS, PKI, certificate, public key, private key, and signature.

##### TLS (Transport Layer Security)

**TLS** is a cryptographic protocol that secures communication over networks (e.g., HTTPS). It ensures:

* **Confidentiality**: Data is encrypted.
* **Integrity**: Data isn't tampered with.
* **Authentication**: Verifies the server (and sometimes the client).

Example: When visit `https://google.com`, your browser uses TLS to encrypt the connection so that no one can spy or tamper with it.


##### PKI (Public Key Infrastructure)

**PKI** is the framework that supports TLS. It includes:

* Certificate Authorities (CAs)
* Digital certificates
* Public/Private key pairs
* Protocols for key management and revocation

PKI lets you trust that `https://bank.com` really belongs to your bank — because a trusted CA vouches for it.


#####  Certificate

A **digital certificate** is like an ID card for websites or users. It contains:

* Subject (e.g., domain name)
* Public key
* Issuer (CA)
* Signature from the CA

It proves: “This public key belongs to bank.com — signed by a trusted CA.”


#####  Public Key and Private Key

These come in pairs and are used in **asymmetric encryption**:

* **Public Key**:

    * Can be shared with anyone.
    * Used to encrypt data or verify a signature.

* **Private Key**:

    * Must be kept secret.
    * Used to decrypt data or create a digital signature.

Example: If Alice wants to send a secret message to Bob, she encrypts it with Bob’s public key. Only Bob can decrypt it with his private key.


#####  Signature

A **digital signature** is created by hashing data and encrypting the hash with a private key. It ensures:

* **Integrity**: The data hasn’t changed.
* **Authenticity**: It really came from the sender.

If a message is signed by a trusted party’s private key, anyone can verify it using their public key.

6. Explain HTTP Session?

* **HTTP Session** stores user-specific data on the server side across multiple HTTP requests.
* It is identified using a **session ID**, often stored in a **cookie (JSESSIONID)**.
* Common uses:

    * Keeping a user logged in
    * Storing user preferences
    * Shopping cart data

In Java:

```java
HttpSession session = request.getSession();
session.setAttribute("username", "vivianna");
```

7.  Explain Cookie? 
* A **cookie** is a small piece of data stored **on the client (browser)** and sent with each HTTP request to the server.
* It can hold data such as:

    * Session IDs
    * User preferences
    * Tracking info

Example:

```http
Set-Cookie: userId=1234; Max-Age=3600; Path=/; HttpOnly
```


8. Compare Session and Cookie?

| **Aspect**     | **Session**                         | **Cookie**                                                |
| -------------- | ----------------------------------- | --------------------------------------------------------- |
| **Storage**    | Server-side                         | Client-side (browser)                                     |
| **Size Limit** | Large (memory-based)                | Small (usually <4KB)                                      |
| **Security**   | More secure (not exposed to client) | Less secure (can be modified by client if not `HttpOnly`) |
| **Use Case**   | Login state, sensitive data         | Preferences, session ID                                   |
| **Lifespan**   | Until session timeout or logout     | Configurable via expiration time                          |

10. How do we use session and cookie to keep user information across the the application?
* **Session:** Stored **on the server**, identified by a unique session ID.
* **Cookie:** Stored **on the client** (browser), can hold the session ID.

**How it works:**

1. User logs in → server creates a session (`HttpSession`) → stores user info (e.g., userId).
2. Server sends a **Set-Cookie** header with the session ID.
3. Browser stores the cookie and sends it in every request (`Cookie: JSESSIONID=xyz`).
4. Server reads the session ID, retrieves the session data.

**Session = actual data on server**, **Cookie = just the ID to find the session**.

12. Explain bearer token and how JWT works.

* **Bearer Token:** A token that grants access. Sent in headers:

  ```
  Authorization: Bearer <token>
  ```

* **JWT (JSON Web Token):** A self-contained token with user info, signed by the server.

**JWT Structure (3 parts, base64-encoded):**

```
header.payload.signature
```

* Header: `{ "alg": "HS256", "typ": "JWT" }`
* Payload: `{ "sub": "123", "role": "admin", "exp": 1710000000 }`
* Signature: `HMACSHA256(base64(header) + "." + base64(payload), secret)`

The server can **verify** the token without storing any session.


13. Explain how do we store sensitive user information such as password and credit card number in DB?

**Never store them in plain text.**

#### For passwords:

* Use **one-way hashing algorithms**: `bcrypt`, `scrypt`, or `Argon2`.
* In Spring: `BCryptPasswordEncoder`

```java
String hashedPassword = passwordEncoder.encode(plainPassword);
```

#### For credit cards:

* Prefer not to store at all.
* If needed, **encrypt** with a strong symmetric key (AES-256), and **rotate keys** regularly.

15. What is the disadvantage of Session? how to overcome the disadvantage?

**Disadvantages:**
* Session is stored **on the server**, consuming memory.
* Not scalable across multiple servers unless using shared session store (e.g., Redis).
* Session ID can be hijacked if not secure (XSS/CSRF).

**Alternatives:**
* Use **stateless JWT tokens** → store auth info in the token, no need for server session.
* Use **Spring Session** with **Redis** for distributed session management.


16. how to get value from application.properties in Spring security?

Use `@Value` or `@ConfigurationProperties`.
```java
@Value("${jwt.secret}")
private String jwtSecret;
```
Or:
```java
@ConfigurationProperties(prefix = "jwt")
public class JwtConfig {
    private String secret;
}
```

17. What is the role of configure(HttpSecurity http) and configure(AuthenticationManagerBuilder auth)?

**`configure(HttpSecurity http)`**:

* Defines **which URLs are secured**, **login/logout**, **CORS/CSRF**, etc.
  ```java
  http
    .authorizeRequests()
      .antMatchers("/admin/**").hasRole("ADMIN")
      .anyRequest().authenticated()
    .and()
      .formLogin();
  ```

* **`configure(AuthenticationManagerBuilder auth)`**:

    * Configures how authentication is handled (e.g., DB, in-memory, LDAP).

  ```java
  auth.userDetailsService(myUserDetailsService).passwordEncoder(new BCryptPasswordEncoder());
  ```

19. Explain best practices to securely store secrets in applications.
* **Never hardcode secrets in code**.
* Use environment variables or `application.properties`, but don't commit them.
* Store sensitive secrets in **secret managers**:

    * AWS Secrets Manager
    * HashiCorp Vault
    * Azure Key Vault
    * Spring Cloud Config with encryption
* Rotate secrets regularly.
* Use encryption-at-rest and encryption-in-transit.
* Limit access via IAM roles/policies.
* Don’t log secrets accidentally.
