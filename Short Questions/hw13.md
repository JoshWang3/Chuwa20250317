# 2. Architecture Styles – Monolithic vs SOA vs Microservices

## Monolithic Architecture

### Definition:
A **single unified application** where all components (UI, business logic, data access) are bundled together and deployed as one.

### Characteristics:
- One deployable unit 
- Tight coupling between modules
- Shared database

---

## Service-Oriented Architecture (SOA)

### Definition:
A system design pattern where software components are **organized as interoperable services**, often communicating via an enterprise bus (ESB).

### Characteristics:
- Services communicate over **SOAP/XML** or **HTTP**
- Uses **Enterprise Service Bus (ESB)** for routing
- Emphasizes **reusability** and **integration**

---

## Microservice Architecture

### Definition:
A system composed of **independent, loosely-coupled services**, each focused on a specific business function and deployed independently.

### Characteristics:
- Services communicate over **REST**, **gRPC**, or **message queues**
- Each service has its own **database**
- Services can be deployed, updated, and scaled individually

---

# 3. Microservice Architecture and Core Components


## Microservice Architecture

**Microservice architecture** is a design style where a large application is composed of **small, independently deployable services**, each responsible for a single business capability.


## Core Characteristics

- **Independent services**: Each service is self-contained and runs in its own process.
- **Decentralized data**: Each service has its **own database**.
- **Lightweight communication**: Services communicate via **REST**, **gRPC**, or **message brokers**.
- **Independent deployment**: Services can be developed, deployed, and scaled independently.
- **Domain-driven design**: Each service maps to a specific business domain.


## Core Components in a Microservice System

| Component             | Role |
|------------------------|------|
| **API Gateway**        | Routes external requests to appropriate services, handles cross-cutting concerns like auth/logging. |
| **Service Registry**   | Keeps track of all available services (like Eureka). |
| **Service Discovery**  | Allows services to find and communicate with each other dynamically. |
| **Config Server**      | Centralizes configuration for all microservices. |
| **Load Balancer**      | Distributes traffic across multiple service instances. |
| **Circuit Breaker**    | Prevents cascading failures if a service goes down. |
| **Monitoring/Tracing** | Observes service health, performance, and dependencies. |
| **Centralized Logging**| Aggregates logs from all services into a single place. |
| **Message Broker**     | Facilitates asynchronous communication (Kafka, RabbitMQ). |
| **Security (AuthN/Z)** | Manages authentication/authorization, often via OAuth2, JWT. |

# 4. Resilience Patterns & Circuit Breaker with Hystrix

## Resilience Patterns:

Resilience patterns help microservices **gracefully handle failures** in distributed systems. These patterns ensure system stability, responsiveness, and fault isolation.


## Common Resilience Patterns

| Pattern           | Description                                                                 |
|-------------------|-----------------------------------------------------------------------------|
| **Retry**         | Retry a failed request a fixed number of times before failing permanently.  |
| **Circuit Breaker** | Prevents repeated calls to a failing service by "breaking the circuit".     |
| **Bulkhead**      | Isolates failures in one service/instance from affecting others.             |
| **Rate Limiter**  | Limits the number of calls within a time window.                            |
| **Fallback**      | Provides a default response or alternative logic when service fails.         |
| **Timeout**       | Fails requests that exceed expected response time.                          |

---

## Circuit Breaker Explained

A **Circuit Breaker** protects your system from repeatedly calling a failing service.  
It has 3 states:

- **Closed**: Normal behavior, calls pass through
- **Open**: Calls fail fast, no calls forwarded
- **Half-Open**: Sends limited calls to test if the service has recovered

If a service fails repeatedly, the circuit “opens” and stops further traffic for a time.

### Enable Hystrix

```java
@SpringBootApplication
@EnableCircuitBreaker
public class App {
    public static void main(String[] args) {
        SpringApplication.run(App.class, args);
    }
}
```


### Add Circuit Breaker to Your Method

```java
@Service
public class UserService {

    @HystrixCommand(fallbackMethod = "getDefaultUser")
    public String getUser() {
        // Simulate remote call
        if (new Random().nextBoolean()) {
            throw new RuntimeException("User service is down!");
        }
        return "User: Alice";
    }

    public String getDefaultUser() {
        return "User: Default";
    }
}
```

# 5. Load Balancing Algorithms in Microservices

## What Is Load Balancing?

Load balancing is the process of distributing incoming network traffic across multiple backend servers or services. In a microservices system, it ensures that:

- No single service instance is overwhelmed
- Traffic is evenly distributed
- High availability and fault tolerance are maintained

## Algorithm Details

### Round Robin
- Each request is forwarded to the next available instance in order.
- Easy to implement, no server health awareness.

### Random
- Selects a random instance each time.
- Works well when instances are equally capable.

### 3. Weighted Round Robin
- Assigns a **weight** to each instance.
- Example: Instance A = 3, B = 1 → A gets 3x more requests.

### 4. Least Connections
- Tracks how many active requests each instance has.
- Sends traffic to the one with the **least load**.

### 5. IP Hash
- Uses a hash of the client’s IP address.
- Ensures **session stickiness**: same client always routes to same server.

# 6. What Is an API Gateway?

## Definition

An **API Gateway** is a server that sits **between clients and microservices**, acting as a **reverse proxy** that:

- Accepts all incoming API requests
- Routes them to appropriate backend services
- Aggregates responses
- Handles cross-cutting concerns (auth, logging, throttling, etc.)

## Responsibilities of an API Gateway

| Responsibility           | Example                     |
|--------------------------|-----------------------------|
| Request routing          | `/orders` → `order-service` |
| Authentication & JWT     | OAuth2, API keys            |
| Rate limiting & throttling| Prevent abuse               |
| Caching                  | Cache popular GET responses |
| Response transformation  | Reformat or combine results |
| Circuit breaking         | Fallback if service fails   |

# 7: Service Discovery and Service Registry

## What Is Service Discovery?

**Service Discovery** is the automatic process by which microservices **locate each other** over the network without hardcoding IP addresses or URLs.

## What Is a Service Registry?

A **Service Registry** is a central database (or service) that keeps track of:
- What services are available
- Where (IP/port) they are running
- Their health status

Microservices **register themselves** with the registry and **query it** to find other services.

## Service Discovery Flow

### 1. **Registration**
When a service starts, it registers itself with the registry.

### 2. **Discovery**
Other services query the registry to get the address of the target service.

### 3. **Health Checks**
The registry keeps track of service availability using heartbeats or health endpoints.
