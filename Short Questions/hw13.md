### 2. Explain monolithic architecture, service oriented architecture and Micro service architecture.
1. **Monolithic Architecture**: A single unified application where all components (UI, business logic, data access) are tightly coupled and run as one.
2. **Service-Oriented Architecture**: Application is broken down into reusable services, which can be shared across systems. Often uses Enterprise Service Bus (ESB) to communicate.
3. **Microservices Architecture**: Application is split into independent, loosely coupled services, each owning its own data and logic, often communicating via REST/gRPC.

Feature | Monolithic | SOA | Microservices
--- | --- | --- | ---
Deployment | One unit | Multiple shared services | Independent services
Scalability | Whole app | Limited service scaling | Fine-grained scaling
Coupling | Tight | Medium | Loose
Communication | In-process calls | ESB (SOAP/XML) | Lightweight (REST/gRPC)
Tech Stack | Usually uniform | Mixed (limited) | Polyglot-friendly
Fault Isolation | Low | Medium | High
### 3. Document the microservice architeture and core components
1. API Gateway  
Acts as a single entry point for clients. Handles request routing, load balancing, authentication, and more.  
Example: Spring Cloud Gateway, Kong, Nginx
2. Service Registry & Discovery  
Keeps track of all active services and their instances. Enables dynamic discovery and load balancing.  
Example: Eureka, Consul, Zookeeper
3. Config Server / Centralized Configuration  
Stores configuration settings for all services centrally. Supports dynamic updates without redeploying.  
Example: Spring Cloud Config, Consul KV
4. Inter-Service Communication  
Services communicate via: Synchronous (REST/gRPC), Asynchronous (Messaging/Events).  
Example: RabbitMQ, Kafka, gRPC, REST
5. Database per Service  
Each microservice manages its own database/schema. Promotes loose coupling and data ownership.  
Supports: SQL, NoSQL, or Polyglot persistence  
6. Circuit Breaker / Resilience  
Prevents cascading failures. Fallback logic and retries when services fail.  
Example: Resilience4j, Hystrix (deprecated)
7. Observability  
Includes logging, monitoring, and tracing.  
Tools: Logging: ELK Stack, Fluentd; Monitoring: Prometheus + Grafana; Tracing: Zipkin, Jaeger, Spring Cloud Sleuth
8. Security  
API Gateway enforces authentication & authorization. Services often use OAuth2 / JWT for identity.  
Example: Keycloak, Auth0, Spring Security
9. CI/CD Pipeline  
Automates testing, building, and deployment of each service independently.  
Tools: Jenkins, GitHub Actions, ArgoCD, Spinnaker
10. Containerization & Orchestration  
Services are deployed as containers. Orchestration platforms manage scaling, networking, and recovery.  
Tools: Docker, Kubernetes
### 4. Explain Resilience patterns? Explain circuit breaker with Spring Cloud Hystrix code example.
Resilience patterns help microservices survive failures and remain responsive. These are especially critical in distributed systems where one service failure can cascade into others.  
Common Resilience Patterns:
1. Circuit Breaker: Stops calling a failing service temporarily.
2. Retry: Automatically retries a failed call.
3. Timeout: Limits the time a service waits for a response.
4. Bulkhead: Isolates failures to prevent one service from exhausting shared resources.
5. Fallback: Provides a default response when a service fails.
6. Rate Limiting: Limits how often services are called to avoid overload.

Circuit breaker with Spring Cloud Hystrix:
```java
@Service
public class ProductServiceClient {

    @HystrixCommand(fallbackMethod = "getDefaultProduct")
    public Product getProductById(String id) {
        // Simulate remote service call
        return restTemplate.getForObject("http://product-service/products/" + id, Product.class);
    }

    public Product getDefaultProduct(String id) {
        return new Product(id, "Default Product", "Fallback description");
    }
}
```
### 5. Explain load balancing algorithms.
1. Round Robin  
Requests are distributed to servers in a circular order. Simple and effective when all servers have similar capacity.  
Pros: Easy to implement  
Cons: Doesn't account for server load or performance
2. Weighted Round Robin  
Like Round Robin, but assigns weights to each server based on capacity.  
Pros: Better for heterogeneous servers  
Cons: Needs manual tuning of weights
3. Least Connections
New request goes to the server with the fewest active connections.  
Pros: Dynamic and efficient under varying loads  
Cons: Doesn't consider request complexity or duration
4. Weighted Least Connections
Combines Least Connections with server weights.  
Pros: Accounts for both load and server capacity  
Cons: More complex to calculate in real-time
5. IP Hash  
Uses client IP to determine which server will handle the request (via a hash function). Ensures the same client always hits the same server.  
Pros: Good for session persistence  
Cons: Uneven load distribution if IPs are clustered
6. Random  
Randomly selects a backend server.  
Pros: Very simple  
Cons: Load distribution can be poor
7. Consistent Hashing  
Requests are mapped to servers using a hash ring. Minimal disruption when a server is added or removed.  
Pros: Ideal for distributed caching & stateful services  
Cons: More complex algorithm
### 6. Explain API Gateway.
An API Gateway is a single entry point for all client requests in a microservices system. It acts as a reverse proxy that routes requests to the appropriate backend services, handles common cross-cutting concerns, and improves manageability.
### 7. Explain service discovery and service registry
- **Service Discovery**: Service Discovery is the process of automatically locating services in a distributed system. Since microservices often run on dynamic IPs (containers, autoscaling, etc.), hardcoding service addresses is not reliable.
- **Service Registry**: A Service Registry is a central database where all services register themselves and lookup other services.
- How It Works  
1. Registration  
When a service starts, it registers itself with the service registry (name, host, port, etc.).
2. Discovery  
When another service needs to call it, it queries the registry to find its location.
3. Deregistration  
When a service shuts down or crashes, it's removed from the registry (either manually or via heartbeat failure).
