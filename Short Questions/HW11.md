# Explain monolithic architecture, service oriented architecture and Micro service architecture.
## Monolithic Architecture
All components of the application (UI, business logic, data access, etc.) are packaged together and run as a single unit (process/application).
### Characteristics:
- **Single codebase:** One large codebase for the entire application.
- **Tightly coupled:** All functions are interconnected.
- **Simple to develop/deploy:** Easier for small-scale applications.
- **Scaling:** Can only scale by running multiple copies of the whole application.
### Example:
- An e-commerce app where user management, product catalog, order processing, and payment are all in one project and deployed together.

## Service-Oriented Architecture
The application is divided into multiple services that communicate over a network (often using protocols like SOAP). Each service handles a specific business function.
### Characteristics:
- **Loosely coupled services:** Services can interact via well-defined interfaces (often XML/SOAP over HTTP).
- **Enterprise Service Bus (ESB):** Central component for routing, transformation, and integration of messages.
- **Reuse:** Encourages reusing existing services across different applications.
- **Interoperability:** Services can be built in different languages/technologies.

## Microservice Architecture
The application is decomposed into small, independent services. Each microservice is self-contained, implements a specific business capability, and can be developed, deployed, and scaled independently.
### Characteristics:
- **Single responsibility:** Each microservice focuses on a single functionality.
- **Own database:** Often, each microservice has its own database.
- **Lightweight communication:** Usually via RESTful APIs, gRPC, or lightweight messaging.
- **Technology diversity:** Teams can choose different tech stacks for different microservices.
- **Independent deployment:** Can update/scale parts of the system independently.
### Example:
- An online store with separate microservices for user profiles, inventory, checkout, payments, and reviews. Each runs and scales separately and communicates via REST APIs.

# Document the microservice architeture and core components
## Microservices
- **Definition:** Small, self-contained, and independent units, each responsible for a single business function (e.g., user management, payment, inventory).
- **Characteristics:**
    - Own codebase and lifecycle.
    - Can be written in different programming languages.
    - Usually has its own data storage.
## API Gateway
- **Definition:** A single entry point for all client requests.
- **Functions:**
    - Request routing to appropriate microservices.
    - Aggregation of results from multiple services.
    - Security, authentication, rate limiting, logging, and monitoring.
## Service Discovery
- **Definition:** Mechanism for automatically detecting and tracking service instances.
- **Functions:**
    - Keeps a registry of active service instances and their addresses.
    - Allows microservices to find each other dynamically.
## Load Balancer
- **Definition:** Distributes incoming network requests evenly across multiple instances of microservices.
- **Functions:**
    - Ensures high availability and reliability.
    - Improves scalability and performance.
## Database per Service
- **Definition:** Each microservice manages its own database, encapsulating its data.
- **Functions:**
    - Avoids tight coupling at the data layer.
    - Enables polyglot persistence (different databases/technologies for different services).
## Centralized Logging and Monitoring
- **Definition:** Tools and infrastructure to collect, store, and analyze logs and metrics from all services.
- **Functions:**
    - Provides observability for debugging and auditing.
    - Examples: ELK Stack (Elasticsearch, Logstash, Kibana), Prometheus, Grafana.
## Configuration Management
- **Definition:** Centralized system to manage and distribute configuration settings across microservices.
- **Functions:**
    - Dynamic updates without redeploying services.
    - Example tools: Spring Cloud Config, Consul.
## CI/CD Pipeline
- **Definition:** Continuous Integration and Continuous Deployment pipelines to automate build, test, and deployment processes.
- **Functions:**
    - Ensures fast, reliable delivery of features and fixes.
    - Enables independent deployment of each microservice.
## Inter-Service Communication
- **Definition:** Mechanisms by which services communicate, usually via:
    - **Synchronous:** HTTP/REST, gRPC.
    - **Asynchronous:** Message queues (RabbitMQ, Kafka).
## Security
- **Definition:** Authentication and authorization across distributed services.
- **Functions:**
    - OAuth2, JWT, API keys.
    - Secure internal and external communication.

# Explain Resilience patterns? Explain circuit breaker with Spring Cloud Hystrix code example.
## Resilience Patterns in Microservices
### Circuit Breaker
- Prevents repeated failures when a service is down by “breaking the circuit” and returning errors immediately instead of making actual calls.
- After a timeout, it allows some requests to see if the service has recovered.

### Retry
- Automatically retries failed requests a certain number of times before giving up.

### Fallback
- Provides an alternative response (default data or cached data) when a service call fails.

### Bulkhead
- Isolates resources (threads, pools) for different services/components so that a failure in one does not cascade to others.

### Timeout
- Sets a maximum duration for external service calls to avoid hanging indefinitely.

## Circuit Breaker Pattern Explained
What it does:
- Monitors service calls.
- If failures reach a threshold, it “opens” the circuit to block further calls temporarily.
- After a cooldown period, it allows a few test calls (“half-open” state). If successful, it “closes” the circuit; otherwise, it stays open.

### Code Example:
#### Add Dependencies (Maven)
```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-hystrix</artifactId>
</dependency>
```
#### Enable Hystrix in Spring Boot Application
```java
@SpringBootApplication
@EnableCircuitBreaker   // or @EnableHystrixDashboard for monitoring
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}
```
#### Annotate Service Methods with @HystrixCommand
```java
@Service
public class UserService {

    @HystrixCommand(fallbackMethod = "getUserFallback")
    public User getUserById(String userId) {
        // Imagine this calls another microservice that may fail
        return restTemplate.getForObject("http://user-service/users/" + userId, User.class);
    }

    // Fallback method signature must match the original
    public User getUserFallback(String userId) {
        // Return default user or cached data
        return new User("default", "Unavailable");
    }
}
```
#### RestTemplate Bean with Load Balancer
```java
@Bean
@LoadBalanced
public RestTemplate restTemplate() {
    return new RestTemplate();
}
```
#### Example Controller
```java
@RestController
public class UserController {

    @Autowired
    private UserService userService;

    @GetMapping("/user/{id}")
    public User getUser(@PathVariable String id) {
        return userService.getUserById(id);
    }
}
```

# Explain load balancing algorithms.
## Round Robin
- **How it works:** Requests are distributed sequentially across the list of servers.
- **Example:** First request to Server A, second to Server B, third to Server C, then back to A.
- **Best for:** Servers with similar specs and workloads.
## Weighted Round Robin
- **How it works:** Like Round Robin, but assigns a weight to each server. Servers with higher weights get more requests.
- **Example:** Server A (weight 3), B (weight 1), C (weight 1) → Out of 5 requests, A gets 3, B and C each get 1.
- **Best for:** When servers have different capacities.
## Least Connections
- **How it works:** Sends each new request to the server with the fewest active connections.
- **Best for:** When requests have variable processing times, or when some servers are faster.
## Weighted Least Connections
- **How it works:** Combines “least connections” with server weights—more powerful servers can handle more simultaneous connections.
- **Best for:** Environments with variable server performance.
## IP Hash
- **How it works:** Uses a hash of the client’s IP address to determine which server will handle the request.
- **Benefit:** Requests from the same client/IP go to the same server (sticky sessions).
- **Best for:** Session persistence without external session stores.
## Random
- **How it works:** Selects a server at random for each request.
- **Benefit:** Simple, can be effective in evenly loaded environments.
## Resource/Response Time Based
- **How it works:** Routes requests to the server with the most available resources (CPU/memory) or lowest response time.
- **Best for:** Highly dynamic environments or real-time applications.

# Explain API Gateway.
API Gateway is a server (or service) that acts as a single entry point for all client requests to a system of microservices. It manages, routes, secures, and sometimes transforms these requests before they reach the appropriate backend service.
## Key Functions of an API Gateway
- **Request Routing**
    - Forwards incoming client requests to the correct microservice(s).
    - Can aggregate data from multiple services and return a single, unified response.
- **Security & Authentication**
    - Central point for handling authentication (OAuth2, JWT, API keys).
    - Can enforce security policies, rate limiting, and access control.
- **Load Balancing**
    - Distributes incoming requests across available instances of backend services.
- **Request/Response Transformation**
    - Can modify request/response formats (e.g., protocol translation, versioning).
- **Monitoring & Logging**
    - Central place for capturing logs, analytics, and metrics about API usage and performance.
- **Caching**
    - Can cache common or repeated responses to reduce load on backend services.
- **Throttling & Rate Limiting**
    - Controls the number of requests allowed for specific users, clients, or APIs.
- **Service Discovery Integration**
    - Can dynamically route to services as they are registered/unregistered (especially in dynamic cloud environments).

## Why Use an API Gateway?
- **Simplifies client interaction:** Clients don’t need to know the location or number of microservices.
- **Reduces client complexity:** One URL/endpoint to call instead of many.
- **Centralized security and monitoring:** Easier to implement and audit.
- **Handles cross-cutting concerns:** Like authentication, logging, and rate limiting in one place, rather than in every service.

# Explain service discovery and service registry
## Service Discovery
Service discovery is the automatic process of detecting network locations of microservice instances within a distributed system.
- It enables services to find and communicate with each other dynamically without hardcoding addresses (IP/port).

### Why is it needed?
- In microservices, services are often deployed dynamically (scaled up/down, moved, updated).
- IP addresses and ports can change frequently (especially in cloud or container environments like Kubernetes).
- Manual configuration is error-prone and not scalable.

### How does it work?
- When a new service instance starts, it registers itself with a central registry.
- When a service needs to communicate with another, it queries the registry to discover the current location (IP/port) of the target service.

## Service Registry
A service registry is a central database (or server) that keeps track of all available service instances and their network locations.

### Core responsibilities:
- **Registration:** Services register themselves (or are registered) with the registry, providing their network details.
- **Deregistration:** When a service goes offline, it is removed from the registry.
- **Querying:** Services or load balancers ask the registry for up-to-date locations of other services.
